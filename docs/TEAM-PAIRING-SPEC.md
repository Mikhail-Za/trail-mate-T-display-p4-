# Team Pairing: Authenticated Key Exchange Spec (v2)

Author: Fable, 2026-07-04. Written against the real firmware at commit-on-disk 2026-07-01, verified by source read + the linked `build.tdisplayp4_tft/trail-mate.map`.
Purpose: replace the in-clear PSK exchange with a MITM-resistant, replay-resistant authenticated key establishment, using the touchscreen as the out-of-band channel. This is a design spec for an Opus/coder session to implement; it introduces no new crypto dependency.

## Problem, from the current code

- The team PSK is transmitted over LoRa in plaintext. Default branch, no passphrase UI is wired (`idf_lora_pairing_service.cpp:153-157`; `setPassphrase()` has no call site anywhere in the repo). Anyone in radio range can read the PSK off a `KeyPacket` (`team_pairing_wire.cpp` encodeKey/decodeKey are pure byte packing, no cipher).
- Key material is weak: `team_id` + PSK are generated by a hand-rolled xorshift32 seeded from `sys::millis_now() ^ 0xA5A55A5A` (`team_page_components.cpp:160-175`), a ~32-bit uptime-derived seed. This is guessable and must not be used for key material.
- Pairing is unauthenticated: `Beacon` carries no anti-spoof token, and `handleJoin` validates only `team_id` (`team_pairing_coordinator.cpp:261-283`), so a rogue member or a spoofed leader is trivial.
- A correct primitive already exists but is dead: the "Option A" mode derives `PSK = SHA256(passphrase||team_id)[:16]` and sends only a sentinel on the wire (`idf_lora_pairing_service.cpp:22-24, 62-81`). It is unreachable from the UI. This spec supersedes it with a scheme that needs no shared secret typed in advance.

## What is already available (verified in the .map, so no new dependency)

- **X25519 ECDH**: `ed25519_key_exchange(out_secret, peer_pub, priv)` (orlp/ed25519, vendored; linked at `trail-mate.map:52720`). Produces a 32-byte shared secret from a Curve25519 keypair.
- **SHA-256**: `IdfTeamCrypto::deriveKey` / `sha256Kdf` (`idf_team_crypto.cpp:27-72`; mbedtls linked).
- **ChaCha20-Poly1305 AEAD**: `IdfTeamCrypto::aeadEncrypt/aeadDecrypt` (`idf_team_crypto.cpp:74-152`; linked at `trail-mate.map:65411`). Has an RFC 8439 known-answer self-test (`runSelfTest`, `:154-246`).
- **Hardware RNG**: `esp_random()` via `TeamRuntimeIdf::fillRandomBytes()` (`team_runtime_idf.cpp:23-53`; linked at `trail-mate.map:33983`). This is the RNG to use for all key material, replacing `next_random_byte()`.

## Threat model

Defends against: a passive eavesdropper on LoRa (must not learn the PSK), an active man-in-the-middle within radio range (must be detected before the PSK is trusted), replay of a past pairing, and a protocol-downgrade attempt that forces the legacy plaintext path.

Does not defend against: a compromised or malicious endpoint device (out of scope; the user holds both devices in the family case), physical coercion, or RF denial of service (an attacker can always jam LoRa; the goal is that jamming causes pairing to *fail*, never to succeed insecurely).

## Design: X25519 ECDH + committed short-authentication-string (SAS)

The PSK is never transmitted. Both devices derive it from an ECDH shared secret. A 6-digit SAS shown on both screens lets the users detect a MITM, using a hash commitment (ZRTP / Bluetooth-Numeric-Comparison style) so the short SAS cannot be brute-forced by an active attacker.

Notation: L = leader, M = joining member. `||` = concatenation. All multi-byte integers big-endian. `esp_random` is the only randomness source.

### Message sequence (pairwise; L runs one instance per joining member, keyed by `member_id||nonceM`)

Bump `kPairingVersion` to 2 and add message types `JoinCommit=4`, `KeyExchange=5`, `Reveal=6`, `Confirm=7`. Every frame keeps the existing 4-byte header (`magic 'T','M'`, version=2, type) and `team_id` (8B). All frames below are well under the ~184B payload limit, so no fragmentation.

1. **Beacon (L to broadcast, repeated at `kBeaconIntervalMs`)** advertises version=2 (secure-capable). Unchanged otherwise. It carries no key, so it stays small and the slow cadence that keeps LVGL responsive is preserved.

2. **JoinCommit (M to L)**, ~44B. M generates an ephemeral X25519 keypair `(privM, pubM)` and a 16-byte `nonceM`, both from `esp_random`. M sends `{ member_id(4B), nonceM(16B), commit(16B) }` where `commit = SHA256("TS-pair-commit-v2" || team_id || pubM || nonceM)[:16]`. M does **not** reveal `pubM` yet. This commitment is the security-critical step: it fixes M's key before M sees L's key.

3. **KeyExchange (L to M)**, ~44B. On JoinCommit, L generates a fresh ephemeral X25519 keypair `(privL, pubL)` per member from `esp_random`, records the commit, and sends `{ nonceM(echo,16B), pubL(32B) }`.

4. **Reveal (M to L)**, ~44B. M sends `{ nonceM(16B), pubM(32B) }`. L verifies `SHA256("TS-pair-commit-v2" || team_id || pubM || nonceM)[:16] == commit`. Mismatch aborts the session (this is a detected attack).

5. Both sides compute the shared secret `ss = X25519(own_eph_priv, peer_eph_pub)` (via `ed25519_key_exchange`) and then:
   - `SAS = ( SHA256("TS-pair-sas-v2" || team_id || pubM || pubL || nonceM) interpreted as a big-endian integer ) mod 1_000_000`, rendered as a zero-padded 6-digit decimal.
   - `PSK = SHA256("TS-pair-psk-v2" || ss || team_id || key_id)[:16]`.

6. **Out-of-band confirm.** Both screens display the same 6-digit SAS. The users compare (in the family case, one person holding both devices checks the numbers match) and each taps Confirm or Reject. A mismatch means a MITM and must abort both sides.

7. **Confirm (both directions), key confirmation**, ~40B. After the user taps Confirm, each side sends an AEAD tag proving it holds the same `PSK`: `Confirm = aeadEncrypt(key = SHA256("TS-pair-kc-v2" || PSK)[:32], nonce = 12 zero bytes, aad = team_id || role, plaintext = empty)`. Each side verifies the peer's tag. This detects the case where the SAS was confirmed but the two sides somehow derived different secrets (bug, or a very lucky attacker), before either device trusts the PSK. Only after a valid peer Confirm does a device store the PSK and mark the team joined.

8. Persist the PSK to NVS via the existing snapshot store (`idf_nvs_team_ui_snapshot_store.cpp`, namespace `team_keys`). Note: NVS persistence appears already implemented on disk (this supersedes the stale "re-pairs every reboot" memory note), but one binding line was not directly viewed. Confirm `saveKeysNow()` routes to this store and not a RAM-only store before closing that item.

### Why the commitment makes a 6-digit SAS safe

Without the commitment, an active MITM E relays between M and L: M sees E's key (thinking it is L), L sees E's key (thinking it is M). The SAS each user sees is computed over the keys they actually received. E wins if she can make M's SAS equal L's SAS. With only a 6-digit (~20-bit) SAS and no commitment, E could grind her two ephemeral keys (~2^20 work) to force a collision, defeating the check.

The commitment removes the grinding. M commits to `pubM` in step 2 before learning `pubL` in step 3, and E (playing fake-M toward L) must likewise commit toward L before seeing L's real key. Both of E's key choices are locked before she sees the honest keys that determine the SAS, so she gets a single blind attempt: collision probability ~2^-20 (about one in a million), with no ability to improve it by grinding. That matches the Bluetooth Numeric Comparison security level. If more margin is wanted, widen the SAS to 7 or 8 digits; the ceremony is unchanged.

### Downgrade, replay, and loss handling

- **Downgrade is refused, not merely detected.** A device the user put into Secure Pairing mode never adopts a PSK received over the air. Since the secure path never transmits a PSK, receiving a plaintext `KeyPacket` (legacy type 3) while in secure mode is by definition an attack or a downgrade attempt and must be rejected. Legacy plaintext pairing remains only behind an explicit, clearly-labeled "insecure pairing" user choice, and a device in secure mode ignores version=1 beacons.
- **Replay** is prevented by fresh per-session `esp_random` ephemeral keys and `nonceM`; the SAS and PSK both bind `nonceM`, and the AEAD key-confirmation binds the derived PSK. A replayed JoinCommit cannot be completed without the matching ephemeral private key.
- **Loss tolerance** over the lossy half-duplex link reuses the existing retry discipline (`kJoinRetryMs`, `kJoinRetryMax`, `kJoinSentHoldMs`, per-state `active_until_ms_` timeouts in `team_pairing_coordinator.cpp:422-475`). Every message is idempotent: the receiver keys on `(member_id, nonceM)` and drops duplicates. Hard rule for the commit-reveal: L must reject a second, different `pubM` for the same `(member_id, nonceM)`, and M must reject a second, different `pubL`; a change mid-session is an attack, not a retransmit.
- **Blocking TX** (`Sx126xRadio::startTransmit` holds the mutex up to `kTxTimeoutUs=3s`, `sx126x_radio.cpp:475-561`) means the ceremony must stay low-message-count. It is: three frames each way plus the user confirm. Keep the leader beacon on its current slow cadence, show a "Pairing..." UI state during the exchange, and do not move team traffic to `startTransmitAsync` (that path is walkie-exclusive via `hasExclusiveHold()` and reusing it would risk the RX-correctness saga documented in the dual-mesh notes).

### State machine (extends the existing coordinator)

Leader per-member: `LeaderBeacon -> AwaitReveal (got JoinCommit, sent KeyExchange) -> AwaitUserConfirm (verified commit, computed SAS) -> AwaitPeerConfirm (user tapped Confirm, sent Confirm) -> Completed`. Member: `MemberScanning -> Committed (sent JoinCommit) -> AwaitKeyExchange -> AwaitUserConfirm (got KeyExchange, sent Reveal, computed SAS) -> AwaitPeerConfirm -> Completed`. Any timeout or a commit/SAS/AEAD mismatch transitions to `Failed -> stop()`. Reuse `kMemberTimeoutMs` / `kLeaderWindowMs` for the outer bounds.

## Test vectors (known-answer, to pin cross-implementation byte-compatibility)

Follow the existing `runSelfTest` pattern (`idf_team_crypto.cpp:154-246`). The implementer generates and commits these once, then asserts them in a self-test so any future refactor or an Arduino/rweather peer stays byte-compatible:

1. Fix `privM`, `privL` (32 bytes each, from a KAT, not `esp_random`), `team_id`, `key_id`, `nonceM`. Compute and pin: `pubM`, `pubL`, `ss`, `commit`, `SAS` (6-digit string), `PSK` (16 bytes), and both `Confirm` AEAD tags, using the exact domain-separation strings and byte layouts above.
2. Assert `SHA256(commit-input)[:16] == commit`, that swapping any input byte changes the SAS, and that the PSK never appears verbatim in any serialized frame (grep the emitted bytes for the PSK; it must be absent).

## Acceptance criteria (Goalkeeper contract hooks)

- A simulated MITM that relays and substitutes keys produces different SAS values on the two ends (test the SAS derivation directly with attacker-substituted keys), and the AEAD key-confirmation fails when the two sides hold different `ss`.
- A device in secure mode rejects a plaintext legacy `KeyPacket` and a version=1 beacon.
- Dropped/duplicated frames at each step still converge (loss-injection test), and a changed `pubM`/`pubL` mid-session aborts.
- All key material comes from `fillRandomBytes` (`esp_random`); a static check confirms `next_random_byte()` is no longer on the pairing key-generation path.
- The self-test known-answer vectors pass, and the PSK-absent-from-wire assertion passes.

## First implementation step (highest value, smallest change)

Even before the full ceremony ships, swap `team_id`/PSK generation from `next_random_byte()` (xorshift, `team_page_components.cpp:160-175`) to `TeamRuntimeIdf::fillRandomBytes` (`esp_random`). This removes the guessable-seed weakness immediately and is independent of the rest of the spec.
